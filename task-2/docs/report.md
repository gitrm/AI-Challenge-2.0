# Gatherwave — Build Report

## Origin

The original build plan (`/.lovable/plan.md`) was generated by **Claude Opus
4.7 (`/docs/lovable-generated-plan.md`)** based on the task description. Lovable then executed the plan
phase-by-phase, adapting it to this template's stack (TanStack Start instead
of React Router DOM) without changing the data model or feature scope.

## Tools and techniques

- **Frontend**: TanStack Start v1 (React 19, Vite 7, file-based routing,
  server functions). Tailwind v4 with a semantic-token design system in
  `src/styles.css` and shadcn/ui primitives.
- **Backend**: Lovable Cloud (managed Postgres + Auth + Storage). All
  business rules live in the database — RLS policies for access control
  and a small set of SECURITY DEFINER RPCs for the operations that need
  atomicity (RSVP + waitlist promotion, invite redemption, cancellation).
- **Realtime**: Supabase Realtime channels on `rsvps` for live counters on
  the check-in screen and instant ticket updates for the attendee.
- **Deployment**: Cloudflare Worker via TanStack Start's Vite plugin.

### Notable libraries

- `qrcode.react` for ticket QR rendering
- `date-fns` + `date-fns-tz` for time-zone-aware formatting
- Browser-native `BarcodeDetector` for QR scanning (with manual entry as the
  always-available fallback so a camera is never required)
- Hand-rolled ICS builder in `src/lib/ics.ts` (avoids a 50KB dependency for
  ~40 lines of code)

## What worked well

- **Pushing logic into Postgres.** RSVP capacity, waitlist FIFO ordering,
  and waitlist promotion on cancellation/capacity-increase are all done in
  triggers and RPCs. The frontend just calls `rsvp_to_event(event_id)` and
  trusts the result. This eliminated entire classes of race conditions and
  kept the React layer simple.
- **RLS as the security model.** Every table is locked down by RLS, so the
  same browser Supabase client is safe for public reads and authenticated
  writes. Helper functions `is_host(host_id)` and `is_member(host_id)` keep
  policies short and readable.
- **Flat routing in TanStack Start.** `host.events.$eventId.check-in.tsx`
  style filenames let the URL structure mirror the file tree without
  nesting layouts we didn't need.
- **Design tokens first.** Defining color/elevation tokens in `styles.css`
  before building screens kept the UI consistent across ~15 routes without
  ever reaching for raw Tailwind colors in components.

## What didn't work / had to be reworked

- **Cryptic route prefixes.** Initial routes used `/e/$eventId` and
  `/h/$slug` (short for "event" / "host"). Real users read the URL and
  found the single-letter prefixes confusing. Renamed to `/event/$eventId`
  and `/hosts/$slug`.
- **Seed data with readable UUIDs.** First pass used IDs like
  `e0000003-0000-0000-0000-000000000001` to make debugging easier. From a
  user's perspective those leaked "this is fake" energy and looked broken
  in the URL bar. Replaced with real `gen_random_uuid()` values via a
  migration that updated PKs and FKs in one transaction.
- **System-info leakage in copy.** Several spots had explainer text written
  for the implementer ("Your host page will be at /h/your-slug",
  "No host exists at /h/{slug}"). Removed or rewritten as user-facing
  copy.
- **Native file inputs.** The default `<input type="file">` rendered the
  "Choose File" button as flat unstyled text inside the input. Restyled
  globally via `file:` Tailwind variants on the shared `Input` component
  so it now reads as a real secondary button with hover state.
- **`SECURITY DEFINER` view linter warning.** A convenience view tripped
  the Supabase linter; refactored to a function so RLS is enforced
  per-call.
- **Loader vs. session race.** Auth-protected server functions called from
  loaders 401'd on first paint because the browser hadn't restored the
  session yet. Standardized on calling protected functions from components
  via `useServerFn` + `useQuery`, and only using loaders for unprotected
  reads.

## Notable decisions

- **No client-side admin checks.** Roles are stored in `host_members` and
  always evaluated server-side via `is_host` / `is_member`. The client
  never decides "is this user a host?" — it asks the database, which
  enforces the answer through RLS.
- **Tickets = `rsvps.ticket_code`.** Rather than a separate `tickets`
  table, the RSVP row *is* the ticket. The `ticket_code` is generated at
  insert time (`upper(substr(encode(gen_random_bytes(6),'hex'),1,8))`) and
  is what the QR encodes. Less moving parts, one source of truth for
  attendance.
- **Manual code entry is first-class.** The check-in flow was designed
  around manual entry from the start. QR scanning is layered on top and
  degrades gracefully where `BarcodeDetector` isn't available.
- **Gallery default = pending.** New uploads land as `pending` and are
  invisible to the public until a host approves. The uploader can still
  see their own pending photo (RLS allows `user_id = auth.uid()`), so
  there's no confusing "did my upload work?" moment.
- **Reports don't auto-hide.** A single report doesn't remove content —
  it surfaces in the host moderation queue, and the host decides. This
  avoids a trivial brigading vector while still giving hosts the tools
  to act fast.
- **No paid events (yet).** The toggle is visible but disabled with a
  "Coming soon" tooltip so the data model already carries `is_paid` and
  the UX surface is reserved.

## Security hardening

After the initial build, several rounds of the security scanner drove a
set of follow-up migrations. The current posture:

- **Event visibility is enforced in RLS, not just in the UI.** The public
  read policy on `events` requires `status = 'published'` *and*
  `visibility = 'public'`. Unlisted/private events are only readable by
  host members (via `is_member(host_id)`), so a direct PostgREST query
  cannot enumerate unlisted events.
- **Host contact email is not readable anonymously.** `SELECT` on the
  `hosts.contact_email` column is revoked from `anon` and `PUBLIC`. The
  public host page (`/hosts/{slug}`) reads only the safe columns
  (id, slug, name, logo_url, bio).
- **Realtime topics are user-scoped.** The realtime topic policy requires
  the channel name to end with `:` + `auth.uid()`, matching the app's
  `tickets:<uid>` and `rsvps:<eventId>:<uid>` patterns. Combined with a
  `user_id=eq.<uid>` postgres_changes filter and the `rsvps_self_read`
  RLS policy, a user cannot subscribe to another user's RSVP stream.
- **Invite tokens are not directly selectable.** `host_invites` has no
  permissive SELECT policy for `anon`/`authenticated`; redemption goes
  through the `redeem_invite` SECURITY DEFINER RPC, which validates the
  token server-side.
